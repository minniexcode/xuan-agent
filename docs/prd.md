## 产品概述

玄枢（xuan-agent）是一个面向传统五术、玄学兴趣和自我探索场景的 AI Agent。它用确定性算法完成排盘与结构化计算，再由 LLM 做中性、可解释、可追问的分析。

V1 聚焦八字命理：基于出生信息完成排盘，并提供通俗/进阶两层结构化解读。相术（面相/手相图像分析）作为 V2 首要扩展方向，不在 V1 范围内。

V1 交付 Agent 核心 + CLI + SDK，第一用户是开发者与有基础的爱好者，用于验证排盘准确性、解读质量和多模型效果。普通兴趣用户是产品的长期服务对象，V1 后经独立前端项目（网页/App）接入，V1 不直接用命令行服务。产品先以个人工具形态验证核心管线，后续再考虑开源、扩展五术模块和面向普通用户的前端形态。

### 产品愿景

让传统五术知识以更低门槛、更结构化、更可追溯、更克制的方式被理解、学习和使用。

玄枢不试图把玄学包装成确定性预测系统，而是把排盘、术语解释、古籍引用、个人档案和连续对话整合成一个适合普通用户自我探索、也适合爱好者进阶研究的工具。

### 产品定位

玄枢的定位是：

- 面向个人使用的玄学分析 Agent
- V1 面向开发者与有基础用户的学习与辅助解读工具，以 CLI + SDK 交付
- 面向普通用户的兴趣型自我探索工具，体验上接近星座、MBTI 等轻量内容（V2 经独立前端项目交付）
- 以八字为 V1 起点、相术为 V2 首要扩展的插件化五术产品
- 架构上支持多 LLM Provider 可切换；多 Provider 对比属 V1 完成后的验证能力，不是 V1 交付卖点

它不是：

- 算命结论生成器
- 吉凶断言系统
- 医疗、法律、投资、婚育等高风险决策工具
- 面部识别或生物特征识别产品

## 背景与动机

传统五术内容门类多、术语密度高、资料来源分散。普通用户可能只是像看星座、MBTI 一样对自我理解、性格倾向和关系话题感兴趣，但一进入八字、十神、神煞、格局等内容，就容易被术语门槛挡住。即使用户已经具备基础，也常会遇到以下问题：

- 普通用户想获得轻量、温和、可分享的自我探索内容，但不希望被恐吓式结论或宿命论标签影响。
- 传统玄学内容常在“娱乐化太浅”和“专业化太难”之间摇摆，缺少可逐层展开的解释体验。
- 八字排盘涉及历法、干支、节气、十神、大运等确定性计算，手工处理容易出错。
- 术语解释散落在不同资料中，用户需要反复检索和对照。
- 古籍原文和现代解释之间缺少可追溯连接，容易变成主观发挥。
- LLM 可以生成流畅文字，但如果让 LLM 直接计算排盘，容易出现干支、十神、日期换算等基础错误。
- 相术分析依赖图像输入，传统文本 Agent 很难覆盖面相和手相场景。
- 不同 LLM Provider 在玄学语境、中文表达、古文理解、视觉分析上的表现差异明显，需要可切换、可比较。

因此，V1 的核心思路是 **计算与解读分离**：

- 确定性排盘由 `tyme4ts` 等确定性计算库完成。
- LLM 不负责算数、不自行推导干支，只基于结构化结果做解释、关联和表达。
- 古籍知识通过 RAG 提供引用依据，降低纯主观生成。
- 通过 Provider 抽象保持多模型可切换；V1 默认使用单一 Provider（DeepSeek），多模型对比作为 V1 完成后的验证能力。

## 参考项目与借鉴方向

本节用于记录 GitHub 开源项目调研结论，作为后续学习和产品设计参考。

这些项目不代表玄枢要直接照搬的实现方案，而是提供可借鉴的产品形态、模块边界和风险提醒。当前判断是：相关方向已有不少开源探索，但多数项目只覆盖八字、占星、手相、面相、RAG、Skill 或 MCP 工具中的一部分，还没有看到一个成熟项目完整覆盖玄枢当前组合。

玄枢的差异点应继续放在：

- 普通用户友好的自我探索体验（V2 经独立前端项目交付）
- 通俗模式 / 进阶模式两层输出
- 八字确定性排盘与 LLM 解读分离
- 相术 Vision 分析与安全边界（V2）
- RAG 古籍引用与可追溯解释
- 多 Provider 对比（V1 完成后验证）
- 对话记忆与用户档案
- Skills 插件化和后续五术扩展

### 调研结论

GitHub 上已经存在八字 Agent、占星 Agent、手相 / 面相 AI、Skill 模板、MCP 占卜工具等项目，说明这个方向不是从零开始。

但现有项目大多偏向以下某一种形态：

- 专业命理报告或命书生成
- 八字排盘 + LLM 解读
- 占星 chart calculation + chatbot
- 手相 / 面相图像分析 demo
- RAG 知识库问答
- Skill 或 MCP 工具封装
- 面向开发者的 Agent 技术实验

对玄枢来说，真正有价值的不是复制某个项目，而是吸收它们已经验证过的设计共识：

- 可靠项目通常会把确定性计算交给规则、库或工具，而不是让 LLM 直接生成排盘。
- LLM 更适合做解释、表达、追问、摘要、引用整合和多风格输出。
- 八字、相术、占卜等能力适合拆成独立 Skill。
- 长报告和复杂分析需要阶段式输出，否则用户会觉得等待过程不可控。
- 图像类相术需要比文本分析更强的隐私提示和边界控制。
- 普通用户体验仍有明显空白，很多项目偏专业、偏命书、偏技术 demo。

### 对玄枢的启发

玄枢后续设计应坚持 **确定性计算 + LLM 解读**。

八字排盘、干支推导、十神映射、大运流年等内容应由 `tyme4ts` 或其他确定性工具完成。LLM 不负责算数，也不应该直接生成排盘结果。LLM 的价值在于把结构化结果解释给不同层级的用户，并支持追问、总结和引用整合。

Skills 插件化方向是合理的。

后续可以把能力拆成：

- `bazi`（V1）
- `xiangshu-face`（V2）
- `xiangshu-palm`（V2）
- `rag-reference`
- `profile`
- `provider-compare`（V1 完成后验证）

这样新增六爻、紫微、奇门、梅花等模块时，只需要新增 Skill 并注册，而不是重写核心 Agent。

普通用户体验应坚持 **通俗模式 / 进阶模式** 两层报告。

很多开源项目更偏专业报告或技术 demo。玄枢应把普通用户作为并列主目标：默认用少术语、短句、关键词、生活化解释和可追问问题承接用户，再允许用户展开四柱、十神、格局、大运、古籍引用等进阶内容。

长报告需要进度感。

八字报告、相术分析和 RAG 引用都可能比较长。后续产品架构可以借鉴 SSE、WebSocket streaming 或阶段式输出，例如：

- 排盘完成
- RAG 检索完成
- 通俗解读生成
- 进阶依据可展开

相术作为 V2 方向，可以先直接用 Vision LLM，稳定后再考虑 CV 标注层。

相术 V2 直接使用各 Provider 的原生 Vision 能力（如 DeepSeek Vision 模型）验证用户体验。等相术方向稳定后，再考虑加入三庭五眼、面部区域、掌纹线条等可视化标注，让普通用户更容易理解报告依据。

安全和隐私不能只写边界提醒。

涉及出生时间、出生地、面相图片、手相图片、用户档案和对话历史时，产品默认流程就应该控制风险：

- 不默认长期保存敏感数据。
- 不在日志中记录 API key 或完整敏感信息。
- 上传图片前提示会发送给对应 LLM Provider。
- 不做身份识别、疾病判断或敏感属性推断。
- 不把玄学分析包装成科学预测或重大决策建议。

这些参考项目说明，玄枢的方向可行；但本产品需要继续强化自己的边界：普通用户友好、中性表达、证据意识、安全默认、Skills 扩展和通俗 / 进阶双层输出。

## 目标用户与场景

### 目标用户

#### 1. 有基础的玄学爱好者（V1 用户）

这类用户了解五行、天干地支、十神、四柱等基础概念，希望借助工具提高排盘、查询和解读效率。

他们不需要产品从零科普所有概念，但需要输出结构清晰、术语准确、可追问。

#### 2. 自学八字的用户（V1 用户）

这类用户正在学习八字命理，希望通过真实案例反复练习。

他们关注：

- 排盘是否准确
- 解读是否有依据
- 是否能解释术语
- 是否能对比不同模型的分析风格（V1 完成后）

#### 3. AI Agent 与传统文化工具探索者（V1 用户）

这类用户希望把五术做成可扩展 Agent，关注插件化 Skills、Provider 抽象、RAG、记忆系统和后续开源可维护性。

他们需要 PRD 阶段先明确产品边界，避免后续架构设计变成“大而全”的玄学平台。

#### 4. 普通兴趣用户（V2 服务对象）

这类用户对五术、星座、MBTI、性格测试、自我探索或传统文化内容感兴趣，但不一定理解天干地支、十神、神煞、格局等术语。

他们关注：

- 能不能快速得到一份容易读懂的自我探索报告
- 能不能用通俗语言解释“这是什么意思”
- 能不能围绕性格、关系、事业倾向、学习成长等话题追问
- 输出是否温和、有趣、不吓人、不宿命论
- 是否能在需要时展开看到更专业的依据

V1 不直接用命令行服务这类用户。V1 交付的 Agent 核心 + SDK 是未来独立前端项目（网页/App）的基础，普通用户经该前端使用通俗模式能力。

### 核心使用场景

#### 场景 1：通俗模式快速自我探索

用户（V1 经 CLI `--mode beginner`，V2 经独立前端项目）输入生日、出生时间等基础信息，希望得到一份像星座或 MBTI 一样容易阅读的分析。

Agent 输出通俗版本，例如：

- 关键词摘要
- 性格与行为模式观察
- 五行结构的生活化解释
- 关系和协作中的可能倾向
- 适合继续追问的问题
- 不确定性与非断言提示

#### 场景 2：八字排盘与结构化分析

用户输入出生年月日时、性别、出生地等信息，系统调用确定性排盘库生成四柱、五行分布、十神、大运等基础信息。

Agent 基于排盘结果输出中性分析，例如：

- 命局结构
- 五行偏重与缺失
- 十神关系
- 大运和流年的观察角度
- 可参考的古籍解释

#### 场景 3：围绕八字结果连续追问

用户在一次分析后继续追问：

- “为什么这里说财星较明显？”
- “这个十神关系和月令有什么关系？”
- “能用更适合初学者的方式解释吗？”
- “能不能说人话，不要太多术语？”

系统需要保留当前对话上下文，并能读取用户档案中的基础出生信息和历史分析摘要。

#### 场景 4：通俗版与进阶版切换

CLI 默认输出进阶版（方便开发者核验排盘与依据），需要时可用 `--mode beginner` 切换通俗版；V2 前端默认通俗版，需要时追问“展开依据”“用专业术语解释”“给我看古籍来源”。

有基础用户可以直接请求进阶版，查看四柱、十神、格局、大运、流年和 RAG 引用。

系统应支持同一份分析在两种表达层级之间切换，而不是把所有专业信息一次性堆给用户。

#### 场景 5：古籍引用辅助学习

用户希望理解某个术语或结论的来源，例如十神、格局、神煞或五行生克。

系统通过 RAG 检索古籍或整理后的知识库，返回简短引用、出处和现代解释，帮助用户学习，而不是把引用当成绝对结论。

## 产品边界与原则

### 做什么

V1 做以下事情：

- 接收用户输入的出生信息并完成八字排盘。
- 使用 LLM 对确定性结果进行中性解读。
- 提供通俗、轻量、可追问的自我探索表达（beginner 模式，主要供 V2 前端使用）。
- 提供术语、结构和依据更完整的专业表达（advanced 模式，V1 CLI 默认）。
- 使用 RAG 检索古籍或知识库内容，辅助解释。
- 记录对话级上下文和用户档案级信息。
- 支持 LLM Provider 可切换（V1 默认单一 Provider，多 Provider 对比留待 V1 完成后）。
- 提供 CLI 和 SDK 两种接入方式；HTTP API 仅保留骨架，非 V1 交付物。

### 不做什么

V1 明确不做以下事情：

- 不做“必然发财”“必有灾祸”“一定离婚”等确定性断言。
- 不直接判定绝对吉凶，不给出恐吓式结论。
- 不做封建迷信式断言，不用宿命论语言强化用户焦虑。
- 不把用户固定贴上不可改变的人格或命运标签。
- 不提供医疗、法律、投资、婚育、生死寿命等高风险决策建议。
- 不将玄学分析表述为科学预测。
- 不让 LLM 直接计算八字排盘、干支、节气、大运等确定性内容。
- 不做面部识别、身份识别或生物特征归档。
- 不从图像推断种族、民族、宗教、政治倾向、健康疾病等敏感属性。
- 不在 V1 中提供完整商业化账号系统、支付系统或公开社区。

### 核心原则

#### 计算与解读分离

排盘、历法换算、干支推导、十神映射等确定性任务由代码和专门库完成。

LLM 只负责：

- 解释结构化结果
- 总结观察角度
- 引用知识库内容
- 回答追问
- 调整表达风格

#### 中性分析

输出应呈现结构、关系、倾向和可观察点，而不是绝对判断。

推荐表达：

- “从传统八字语境看，可以观察到……”
- “这个结构通常会被解释为……”
- “这里更适合理解为一种倾向，而不是确定结果。”

避免表达：

- “你一定会……”
- “这是大凶。”
- “必然破财。”
- “注定婚姻不顺。”

#### 低门槛但不低质

普通用户默认看到通俗、短句、少术语的解释，但底层仍应基于确定性排盘、清晰 Prompt 和可追溯知识库。

产品可以借鉴星座、MBTI 的轻量表达方式，但不能把用户简化成固定标签，也不能牺牲术语准确性。

#### 娱乐化入口，克制化表达

普通用户可以把玄枢当作兴趣内容、自我探索工具或社交话题入口。

系统输出应保持温和、有趣、可讨论，但必须避免恐吓、绝对化和宿命论表达。

#### 可追溯与可解释

当输出涉及古籍观点、术语解释或传统判断依据时，应尽量给出来源或说明依据来自知识库检索。

RAG 引用只作为参考，不作为最终裁决。

#### 隐私优先

出生时间、出生地、面相图片、手相图片、用户档案都属于敏感个人数据。

V1 应尽量支持本地优先存储，并在文档与界面中明确提醒用户数据用途。

#### 插件化扩展

每个能力模块都应作为独立 Skill 设计。V1 只实现八字，但后续新增相术、六爻、紫微、奇门等模块时，应通过新建目录和注册 Skill 的方式扩展，而不是改造核心流程。

## 功能需求（V1 Scope）

本章定义 V1 必须实现的产品需求。每条需求以 `FR` 编号描述，后续产品架构文档和技术设计文档应以这些需求为拆解依据。

本章只给每条 FR 的**索引**（目标 + 验收要点）；完整规格（字段、规则、边界情况、验收测试）见 [`docs/requirements.md`](requirements.md)。

### 八字命理模块

八字命理模块的目标是：接收用户出生信息，完成确定性排盘，生成通俗模式和进阶模式两层解读，并支持用户围绕同一盘继续追问。

#### FR-BAZI-01 出生信息采集

系统应提供八字分析入口，采集完成排盘所需的最小信息；信息缺失或歧义时由 Agent 追问补全。

| 字段 | 必填 | 说明 |
| --- | --- | --- |
| 出生日期 | 是 | 公历 `YYYY-MM-DD`；农历输入需标明历法。 |
| 出生时间 | 是 | `HH:mm`。 |
| 性别 | 是 | 用于大运顺逆。 |
| 历法类型 | 是 | `solar` 或 `lunar`。 |
| 出生地 | 否 | V1 仅作备注，不参与计算。 |
| 输出模式 | 否 | `beginner` 或 `advanced`；CLI 默认 `advanced`，V2 前端默认 `beginner`。 |

验收标准：

- 必填信息齐全时，生成 `BirthInput` 并进入排盘。
- 信息缺失或日期含糊时，交互路径由 Agent 追问补全；程序路径（SDK）返回 `VALIDATION_ERROR`。
- 出生地留空不影响排盘。
- 农历输入应标明已按农历换算。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-BAZI-01。

#### FR-BAZI-02 确定性排盘

系统必须使用确定性排盘库完成八字计算（V1 采用 `tyme4ts`），产出结构化 `BaziChart`，不得让 LLM 直接生成四柱或推导干支。

排盘字段范围、大运默认步数等完整规格见 [`docs/requirements.md`](requirements.md) 的 FR-BAZI-02；节气/流年移 V2（见 ADR-0012）。

验收标准：

- 先生成结构化排盘结果，再进入 LLM 解读流程。
- LLM Prompt 中必须包含结构化排盘结果，而不是只包含用户生日。
- 输出中应标明排盘来源，例如 `tyme4ts` 或后续替代库。
- 排盘失败时，系统应返回明确错误原因，不得让 LLM 编造结果。

#### FR-BAZI-03 通俗模式解读

系统应支持面向普通用户生成通俗模式解读（V1 经 `--mode beginner` 使用，V2 前端默认使用）。输出为结构化 section，内容少术语、生活化、非断言。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-BAZI-03。

验收标准：

- 普通用户不需要理解天干、地支、十神，也能读懂主要结论。
- 输出不得出现“必然”“注定”“一定发财”“大凶”等断言。
- 每次输出都应包含“本分析用于兴趣型自我探索，不作为现实决策依据”的边界提示。

#### FR-BAZI-04 进阶模式解读

系统应支持进阶模式，展开术语、结构与依据。输出为结构化 section，术语直接使用；CLI 默认此模式。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-BAZI-04。

验收标准：

- 不得只重复通俗模式，必须展开至少 4 类专业维度（四柱 / 日主月令 / 五行生克 / 十神）。
- 引用 RAG 内容时（RAG 就绪后），应区分原文、释义和 Agent 总结。

#### FR-BAZI-05 追问与同盘复用

用户在一次分析后继续追问时，系统复用同一份 `BaziChart`，不重新排盘。

V1 支持：解释术语、解释判断、改写输出风格、切换输出模式。"切换 Provider 对比"属 V1 后能力。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-BAZI-05。

验收标准：

- 同一会话内追问不得重新生成不同排盘。
- 用户要求解释术语时，应结合当前盘面说明，而不是只给百科定义。
- 切换输出模式时应保留同一份结构化排盘。

### 记忆系统

记忆系统的目标是：支持连续对话和用户档案复用，同时让用户控制哪些信息被保存。

#### FR-MEM-01 会话记忆

系统应本地保存会话上下文（排盘结果、模式、Provider 等），用于支持连续追问。追问依赖会话，因此会话**自动保存**；不做自动过期，提供 `xuan session clear` 清理。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-MEM-01。

验收标准：

- 同一会话追问时，系统能引用前一轮分析结果。
- 新会话默认不自动读取上一会话内容。

#### FR-MEM-02 用户档案记忆

系统应支持用户显式保存长期档案（本地 JSON）。V1 只存出生信息与偏好。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-MEM-02。

验收标准：

- 默认不写档案（默认临时模式）。
- 首次保存用户档案前必须提示用户确认。
- 用户必须能查看、更新、删除档案。

### RAG 知识库

RAG 知识库的目标是：为术语解释和进阶分析提供可追溯参考，而不是替代产品判断。

#### FR-RAG-01 知识库内容管理

V1 只做知识库**管线与契约**，seed 用几条示例占位；内容等有数据后灌入。每条知识须记录来源与版权状态。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-RAG-01。

验收标准：

- 每条知识内容应记录来源或资料名。
- 不确定版权或来源不明的资料不得作为正式知识库核心内容。
- RAG 内容应支持后续增量更新。

#### FR-RAG-02 检索与引用

系统应在需要解释术语、专业判断或古籍依据时调用 RAG。V1 以关键词检索起步（向量索引留技术设计阶段）。

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-RAG-02。

验收标准：

- 用户追问“依据是什么”时，系统应优先检索 RAG。
- 没有命中可靠资料时，系统应说明“未检索到明确依据”，不得伪造出处。
- 引用必须区分原文、释义和模型总结，服务解释、不应大段堆砌。

### 多 LLM 支持

多 LLM 支持的目标是：让业务逻辑不绑定单一 Provider，支持可切换。V1 默认使用单一 Provider（DeepSeek，经 openai-compatible 接入），多 Provider 对比留待 V1 完成后验证。

#### FR-LLM-01 Provider 配置

系统应支持通过 `.env` 或等价配置切换 LLM Provider。

配置项至少包括：

- 当前 Provider
- 模型名
- API key
- Base URL
- 温度等基础参数
- 是否启用 Vision

验收标准：

- API key 不得写入日志或普通输出。
- Provider 配置缺失时，系统应返回明确错误。
- 普通用户不需要理解 Provider 概念，默认使用当前配置即可。

#### FR-LLM-02 Provider 工厂与统一调用

系统应通过自研 `LlmProvider` 抽象和 Factory Pattern 创建不同 Provider 实例（见 ADR-0011）。

验收标准：

- 八字、相术、RAG 解读和追问流程应复用统一 Provider 调用接口。
- 新增 Provider 时，不应改动八字排盘逻辑或相术业务逻辑。
- Vision 不可用的 Provider 不应进入相术图像分析流程，应提示切换支持 Vision 的模型。

#### FR-LLM-03 多 Provider 对比（V1 完成后验证）

多 Provider 对比是 V1 完成核心功能后的验证能力，不作为 V1 交付卖点。架构应保持“同一输入复用 + 标注 Provider/模型”的能力就绪，但 V1 不要求实现自动评分或对比维度打分。

V1 完成后可按需支持：

- 同一份八字排盘的不同模型解读（例如 DeepSeek 不同模型）
- 同一 RAG 证据下不同模型的表达差异

验收标准（V1 完成后）：

- 对比时必须复用同一份确定性排盘。
- 输出应标明每段结果对应的 Provider 和模型。
- 不做自动评分，只做并列输出；维度评估由用户自行判断。

### 插件化 Skills

插件化 Skills 的目标是：让每个术或子能力可以独立开发、注册和扩展。

#### FR-SKILL-01 V1 Skills 注册

> **V2**：Skill 注册机制移 V2（见 ADR-0012）。V1 以 `XuanAgent` facade 方法提供 bazi/profile/rag。

V1 至少包含以下 Skills：

| Skill | 档位 | 说明 |
| --- | --- | --- |
| `bazi` | V1 交付 | 八字命理排盘与解读。 |
| `profile` | V1 交付 | 用户档案和偏好管理。 |
| `rag-reference` | 骨架 | 古籍和术语检索引用（管线就绪，内容待数据）。 |
| `provider-compare` | 骨架 | 多 Provider 对比（V1 后）。 |

详细规格见 [`docs/requirements.md`](requirements.md) 的 FR-SKILL-01。

验收标准：

- 每个 Skill 必须声明输入、输出、依赖 Provider 类型和安全边界。
- 每个 Skill 必须能被 CLI 和 HTTP API 复用。
- Skill 失败时应返回明确错误，不影响其他 Skill 的注册。

#### FR-SKILL-02 后续扩展规则

> **V2**：随 Skill 注册机制一并延后（见 ADR-0012）。

后续新增六爻、紫微、奇门、梅花等模块时，应通过新 Skill 扩展。

验收标准：

- 新 Skill 不应要求重写核心 Agent 流程。
- 新 Skill 应复用统一记忆、Provider、RAG 和安全边界能力。
- 新 Skill 如果包含确定性计算，必须优先使用规则、库或工具完成计算，再交给 LLM 解读。

## 用户交互流程

### User Journey 1：通俗模式快速自我探索

1. 用户（V2 经前端，V1 经 CLI `--mode beginner`）输入生日、出生时间等基础信息。
2. 系统先完成确定性排盘，再生成通俗解读。
3. Agent 输出关键词、简短解释、可追问问题和边界提醒。
4. 用户可继续追问“这是什么意思”“说人话”“展开专业依据”。
5. 如果用户选择展开，系统切换到进阶模式，展示术语、古籍引用和结构化依据。

示例：

```text
我想像看星座或 MBTI 那样，简单了解一下我的八字特点，不要太专业。
```

示例输出结构：

```text
当前为通俗模式：以下内容用于兴趣型自我探索，不做吉凶判断。

1. 三个关键词
2. 性格与行为模式观察
3. 关系和协作中的可能倾向
4. 可以留意的成长问题
5. 想深入时可以展开的专业依据
```

### User Journey 2：CLI 八字分析

1. 用户在 CLI 中输入出生信息。
2. 系统检查必填字段是否完整。
3. 系统调用排盘库生成结构化八字结果。
4. 系统将排盘结果、用户问题和相关 RAG 检索内容交给 LLM。
5. LLM 输出中性分析。
6. 系统保存本轮对话上下文。
7. 如果用户授权，系统更新用户档案摘要。

示例：

```bash
xuan bazi analyze --date 1995-03-12 --time 08:30 --gender male --calendar solar --place "Shanghai"
```

示例输出结构：

```text
当前分析基于：八字命理 / DeepSeek / tyme4ts 排盘结果

1. 盘面摘要
2. 五行分布
3. 十神关系
4. 大运观察
5. 古籍参考
6. 不确定性与边界
7. 可继续追问的问题
```

### User Journey 3：HTTP API 调用（V1 后 / 骨架）

V1 仅保留 HTTP API 骨架，不作为交付物。V1 后，独立前端或第三方服务可经 HTTP API 接入：

1. 上层应用向 HTTP API 提交八字分析请求。
2. API 层完成参数校验。
3. 对应 Skill 执行排盘、RAG 检索或记忆读写。
4. API 返回结构化结果和自然语言分析。
5. 调用方可以展示给用户或继续发起追问。

### 对话流示例

用户：

```text
我不太懂八字，能不能像星座或 MBTI 那样简单说说我的特点？
```

Agent：

```text
可以。我会用通俗模式解释，把它当作传统文化语境下的自我探索内容，不做吉凶判断，也不会给你贴固定标签。
```

用户：

```text
请帮我分析这个八字，重点看五行结构，不要直接说吉凶。
```

Agent：

```text
我会先基于排盘结果看四柱、日主、月令、五行分布和十神关系。下面的分析只作为传统八字语境下的结构观察，不做确定性吉凶判断。
```

用户：

```text
为什么你说印星这里比较重要？
```

Agent：

```text
这个判断来自排盘中的十神映射和月令环境。简单说，印星在这里更多体现为支持、资源和学习吸收能力的观察角度，并不等于现实中一定会发生某个具体事件。
```

用户：

```text
那我今年到底会不会发财？
```

Agent：

```text
我不能给“会”或“不会”这样的确定性结论。从你的盘面看，财星在当前结构里更接近一种对资源、机会更敏感的倾向，而不是某个具体事件必然发生。我建议把它当作了解自己的观察角度，而不是对结果的断言；如果你想深入，我可以展开这个倾向背后的十神关系和古籍依据。
```

## 接入方式

### CLI

CLI 是 V1 的主要入口，面向个人工具验证和本地使用。

CLI 应支持：

- 八字分析
- 用户档案管理
- Provider 切换
- RAG 检索测试
- 查看当前配置

CLI 不要求 V1 提供完整交互式 TUI。命令式调用优先。

#### CLI 功能边界

CLI 应适合：

- 本地单人使用
- 调试排盘和 Prompt 效果
- 对比多模型输出
- 管理本地用户档案 JSON

CLI 不负责：

- 多用户权限管理
- 公开服务鉴权
- 前端页面展示
- 商业化运营配置

### HTTP API（V1 骨架，非交付物）

HTTP API 面向 V1 后的前端、桌面端、自动化工作流或第三方服务集成，V1 只在仓库中保留骨架，不作为验收交付物。V1 的接入方式是 CLI 与 SDK。

HTTP API 未来应支持：

- 创建八字分析任务
- 发起追问
- 查询用户档案
- 更新或删除用户档案
- 切换或指定 Provider
- 返回结构化结果和自然语言解读

#### HTTP API 功能边界

V1 不交付 HTTP API；后续接口设计（路由、请求字段、响应字段、错误码）留到技术设计文档，且应复用 SDK 而非直接访问排盘、Provider、RAG 或存储。

## 非功能需求

### 性能

V1 性能目标应符合个人工具体验：

- 八字排盘本地计算应在秒级内完成。
- LLM 解读耗时主要取决于 Provider 响应速度。
- Vision 分析允许比纯文本分析更慢，但应给出清晰等待状态。
- RAG 检索应尽量在用户可接受范围内完成，不应明显阻塞主流程。

### 安全

系统应保护以下敏感信息：

- API key
- 出生日期和时间
- 出生地
- 用户档案
- 对话历史
- 面相图片、手相图片（V2 相术引入后同样保护）

V1 应遵循：

- API key 通过 `.env` 或本地安全配置读取，不写入日志。
- 默认不在输出中展示完整敏感配置。
- 用户可选择是否保存长期记忆。
- 删除档案应明确删除本地保存内容。
- 当用户索要吉凶、运势成败等确定性结论时，系统应触发 SafetyGuard 降级：承认诉求 → 说明能力边界 → 转为可观察的结构/倾向 → 不给出是/否结论。该规则应进入系统逻辑和 Prompt，而非仅依赖文档提醒。

### 隐私

产品应清晰提示：

- 哪些数据会被发送给 LLM Provider。
- 哪些数据会被保存在本地。
- 用户如何关闭记忆。
- 用户如何删除档案和历史记录。

如果用户使用云端 LLM Provider，系统应提醒图像和文本内容会发送到对应 Provider。

### 可扩展性

系统应从 V1 起支持：

- 新增 Skills
- 新增 LLM Provider
- 替换排盘库
- 替换向量数据库
- 用户档案从 JSON 升级到 DB
- CLI 和 HTTP API 复用同一套核心能力

### 可维护性

产品需求层面要求：

- 每个 Skill 有明确输入、输出和边界。
- 排盘结果应结构化，便于测试和复用。
- Prompt 应可版本化，便于比较不同模型效果。
- RAG 资料应可追踪来源。
- 安全边界应进入 Prompt 和系统逻辑，而不是只依赖文档提醒。

### 可观测性

V1 应至少记录以下调试信息：

- 当前 Provider
- 当前模型
- 当前 Skill
- 排盘库版本或来源
- RAG 命中文档
- 是否使用用户档案
- 是否保存对话级记忆

日志不得记录完整 API key、完整图片内容或未脱敏敏感信息。

## 未来规划（V2+）

V2+ 可按插件化 Skills 扩展更多五术模块。V1 完成八字核心闭环后，优先推进相术与多 Provider 对比，再扩展其余术数。

### 相术（V2 首要扩展）

新增 `xiangshu-face` 与 `xiangshu-palm` 两个 Skill，接收面相或手相图像，使用 Vision-capable LLM（如 DeepSeek Vision 模型）做观察性分析，输出通俗/进阶两层内容，并严格限制身份识别和敏感属性推断。V2 先直接使用 Vision LLM，稳定后再考虑三庭五眼、面部区域、掌纹线条等 CV 可视化标注层。

### 多 Provider 对比（V1 完成后）

八字核心功能完成后，复用同一份确定性排盘，对不同 Provider/模型（如 DeepSeek 不同模型、后续接入的 Claude/GPT）生成并列解读，标注来源，用于评估术语准确度、中文表达质量和安全边界遵守情况，不做自动评分。

### 六爻

新增六爻 Skill，支持起卦、装卦、六亲、六神、动爻、变卦等结构化分析。

V2 重点仍应保持计算与解读分离，避免让 LLM 自行完成装卦计算。

### 紫微斗数

新增紫微 Skill，支持命盘生成、宫位、主星、辅星、四化等分析。

紫微模块需要更复杂的排盘库或规则引擎，适合在八字 V1 稳定后推进。

### 奇门遁甲

新增奇门 Skill，支持起局、九宫、八门、九星、八神等结构化分析。

奇门涉及时间、局法和流派差异，PRD 阶段应单独确认流派边界。

### 梅花易数

新增梅花 Skill，支持时间起卦、数字起卦、体用关系和变卦分析。

该模块适合做轻量交互式占例分析，但仍需保持中性表达。

### 风水与择日

风水和择日属于更高风险、更复杂的实际决策场景。

V2+ 如果扩展，应优先定位为学习和资料整理工具，不直接给出房产、装修、迁居、婚嫁等重大决策结论。

### 开源规划

个人工具验证稳定后，可考虑开源：

- 核心 Agent 框架
- Skills 插件规范
- Provider 工厂实现
- Prompt 模板
- 示例知识库
- 示例 CLI 和 HTTP API

开源前需要整理：

- 数据版权说明
- 古籍资料来源
- 安全边界提醒
- 隐私默认配置
- 贡献指南
